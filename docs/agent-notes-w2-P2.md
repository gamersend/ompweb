# Wave 2 — Phase 2 (Web Push) agent notes

## What changed

Web Push (VAPID) support for the notification pipeline: a NEW feed row can now
also arrive as an OS push notification when no tab is open, reusing the
existing feed/webhook architecture rather than adding a parallel path.

### Delivery design (the load-bearing decision)

- **Single choke point**: `lib/notify/feed.ts` `pushNotifyRow()` calls
  `dispatchPushForRow(row)` (fire-and-forget, belt-and-braces try/catch) for
  every NEW row. Per-emitter or per-SSE-subscriber hooking was explicitly
  avoided — N observers still mean at most one OS push. The existing feed
  id-dedup happens BEFORE dispatch, so late SSE replays never re-push.
- **Gating** (`lib/push/gate.ts`, pure + unit-tested): push config section
  enabled → not a webhook-failure row (`wherr-` loop guard, mirrors
  webhook.ts) → kind allowed → per-row-id dedup (bounded FIFO set of 1000 ids
  on `globalThis`, hot-reload safe) → quiet hours. Quiet hours suppress the
  push exactly like the browser ping; the feed row always records.
- **Payload** (`lib/push/payload.ts`, pure): `{id, kind, title, body,
  sessionId?}` — title/body REDACTED through `lib/search/redact.ts`
  (feed rows can carry RPC error text; an OS notification is glanceable by
  others), body hard-capped at 300 chars, and a guaranteed-terminating shrink
  loop keeps the serialized JSON ≤ 4000 bytes (Web Push protocol caps at 4096).
- **Send** (`lib/push/send.ts`): `web-push` `sendNotification`, 5 s timeout
  (+1 s race guard), exactly one retry (webhook.ts discipline), 404/410 from
  the push service → subscription pruned. `web-push` is reached via
  `createRequire(import.meta.url)` (lib/omp-stats-db.ts pattern) so the legacy
  CJS dep tree is never statically bundled; only loaded when a push is due.
- All delivery counters/fire-and-forget semantics mirror `lib/notify/webhook.ts`.

## Security notes for the new write surfaces

- `web-push-keys.json` and `web-push-subs.json` are credentials (VAPID
  private key; browser endpoint + keys): mode 0600, atomic writes, corrupt
  files quarantined, never echoed over any route (only the public key and
  counts travel; test-pinned in `lib/push/routes.test.mjs`).
- `/api/push/*` sits behind the same `proxy.ts` web-auth gate as every API
  route and is subject to the cross-origin rejection in
  `lib/request-security.ts`; bodies are byte-bounded
  (`parseJsonWithinLimit`, 413 on overflow); subscription input is validated
  (https endpoint, length caps) before touching the store.
- Push payloads are redacted (`lib/search/redact.ts`) BEFORE transport;
  `sessionTitle`/`projectRoot` (local paths) are never included.
- Deliveries are fire-and-forget with a failure budget (1 retry); dead
  endpoints (404/410) are pruned; a failed push never surfaces as a feed row,
  so no failure loops.

## AGENTS.md-ready section (paste into Key Design Decisions)

### Web Push (VAPID) (`lib/push/`, `/api/push/*`, sw.js, NotificationsConfig) (W2-P2)
- Delivery hooks the SINGLE choke point — `feed.ts` `pushNotifyRow` →
  `dispatchPushForRow` (fire-and-forget, never per-emitter/per-SSE-subscriber).
  Gate (pure, `lib/push/gate.ts`): config `push.enabled` + kind allowlist +
  `wherr-` loop guard + bounded per-row-id dedup + quiet hours (suppression
  mirrors the browser ping; feed still records).
- Payload (`lib/push/payload.ts`) is `{id, kind, title, body, sessionId?}`,
  redacted via `lib/search/redact.ts`, body ≤ 300 chars, JSON ≤ 4 KB — never
  ship raw RPC error text or local paths.
- Stores: `~/.omp/agent/web-push-keys.json` (VAPID pair, first-enable
  generation via `/api/push/status`, mode 0600, atomic) and
  `web-push-subs.json` (entries keyed by sha256(endpoint), cap 20 evict
  oldest, pruned on 404/410). Private key/keys never echo over GET.
- `web-push` is loaded via `createRequire` (`lib/push/webpush-loader.ts`) —
  never a static import into the Next bundle. Send: 5 s timeout, 1 retry,
  same fire-and-forget discipline as `lib/notify/webhook.ts`.
- Routes: `POST /api/push/register` (enables the config push section),
  `POST /api/push/unregister` (last removal disables it), `GET
  /api/push/status` (public key + count), `POST /api/push/test` (same send
  path). All `{success,data}`, nodejs, bounded bodies, no-store.
- sw.js owns `push` (tag = row id, renotify false) + `notificationclick`
  (focus existing client, else open `/?session=<id>`); CACHE_VERSION bumped
  on handler changes; the `lib/pwa-cache-rules.test.mjs` drift guard also
  pins the handlers + version wiring.
- Client flow (`components/NotificationsConfig.tsx`): capability-detect first
  (no PushManager → hint; iOS Safari needs the INSTALLED PWA, 16.4+ → hint),
  permission only from the toggle gesture, subscribe with the server public
  key (base64url→Uint8Array via `lib/push/client.ts`), register, rollback
  unsubscribe on failure. All strings in `push.*` ×3 locales.

## Not done / follow-ups

- No per-kind push toggles in the UI yet: the config section
  (`web-notify-config.json → push.events`) is honored by the gate and PUT is
  wired through, but NotificationsConfig exposes only enable/disable + test;
  kind chips would be a small follow-up (the webhook chips pattern already
  exists).
- `label` is stored/validated but the UI does not collect one (reserved).
- End-to-end push delivery against a real push service (FCM) was not
  exercised in this environment; the send boundary is fully tested against
  the typed facade, and the test route exercises the real send path locally.
